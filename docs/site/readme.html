Reverse Engine Anything Plus

One MCP server for reverse engineering — live Windows debugging plus a 157-tool static-analysis suite for PE/ELF, Mach-O, .NET, APK, IL2CPP, WASM/EVM, firmware, and the web.

Your agent asks questions; rea-plus inspects the binary and answers with evidence, not guesses.

✨ Why rea-plus?

  • 🐞 Real debugging, not screenshots — x64dbg, cdb (WinDbg), and Frida engines behind one frozen 30-tool core: breakpoints, stepping, registers, memory, call stacks, time-travel checkpoints.
  • 🧰 157 static tools — Ghidra headless, rizin/radare2, .NET CIL (dnfile) and ILSpy, jadx/apktool/adb, WASM + EVM, firmware, browser/HAR, UPX, PE/ELF/Mach-O readers, and more.
  • 🤝 Honest by design — a missing backend answers capability_unsupported with an install hint. Nothing fakes a result, errors come back as proper MCP isError, and mutating live-debug calls require confirm:true.
  • 🧩 191 tools, 2 resources, 3 prompts — the full generated catalog lives in docs/TOOLS.md; REA_TOOLSETS lets small-context clients load only a profile slice (see Configuration). Without an HTTP token, only a 44-tool read-only allowlist is registered instead of the full surface.
  • 🔌 Two transports — stdio for local agents, streamable HTTP (/mcp + /health, bearer token, localhost Host/Origin validation) for shared setups.
  • 🧪 Proven, not promised — a 91-file default test lane, Ubuntu CI for the released line, and protocol tests that drive the real compiled server.

🚀 Install

Requirements: Node.js ≥ 20. Everything else (Ghidra, rizin, jadx, Frida tooling, …) is optional — tools light up as backends appear; run doctor to see your machine's map. Windows is required for the live debuggers (x64dbg/cdb/Frida attach); static analysis runs anywhere.

One-click (Cursor / VS Code)

Setup wizard (standalone download)

No npm? Download setup.mjs (+ Windows setup.ps1) from the latest release — needs only Node.js 20+:

node setup.mjs --list        # detect installed clients
node setup.mjs --dry-run     # preview without writing
node setup.mjs --yes         # write MCP config (asks unless --yes)
.\setup.ps1 --list
.\setup.ps1 --yes

Or inside the package: npx -y rea-plus rea-plus-cli setup (same wizard).

npx (no clone)

Any stdio MCP client can launch it straight from the npm registry:

{
  "mcpServers": {
    "rea-plus": {
      "command": "npx",
      "args": ["-y", "rea-plus"]
    }
  }
}
Publishing status: rea-plus@0.8.2 is live on the npm registry and io.github.Alyhnte/rea-plus is published on the MCP Registry. The supported installs are npx -y rea-plus (above) and GHCR (see Docker).

Clone & build

git clone https://github.com/Alyhnte/ReaPlus.git
cd ReaPlus
npm ci
npm run build        # tsc + runtime assets (frida-agent.js, Ghidra scripts) -> dist/
npm start            # stdio server (dist/server.js)

# Optional HTTP transport:
node dist/server.js --transport http --port 3848
# -> GET  http://127.0.0.1:3848/health
# -> POST http://127.0.0.1:3848/mcp

Optional extras

# Browser tools (Playwright is an optional dependency, loaded lazily):
npm i playwright && npx playwright install chromium

Then point your agent at it and ask it to inspect something.

⚙️ How it works

flowchart LR
    A["AI agent / MCP client"] -->|stdio or streamable HTTP| S["rea-plus server"]
    S --> C["Conduit core · 30 frozen tools<br/>x64dbg · cdb · Frida · radare2"]
    S --> D["rea domains · 157 tools<br/>Ghidra · rizin · jadx · dnfile · wabt · Playwright"]
    C --> T["Target binary / live process"]
    D --> T
    C --> E["Evidence bundle + obligation ledger"]
    D --> E
    E --> A
  • Frozen core. The 30 conduit tool names are immutable (src/facade/toolNamespace.ts); renames are forbidden, so existing conduit clients keep working.
  • rea domains. 157 rea_* tools register centrally in src/server/registerReaTools.ts.
  • Confirm gates. Live operations that mutate a target require confirm:true; otherwise you get confirmation_required, never a silent side effect.
  • One catalog. mergedCatalog() (8 conduit + 16 rea prerequisite entries) is the single source doctor reads for versions and download links.
  • Resources + prompts. Two static, read-only resources (rea-plus://server-info, rea-plus://capabilities-safety) and three side-effect-free prompts (packer-triage, dotnet-malware-triage, android-triage) are registered alongside the tools; prompts only return text and never run a tool.
  • Typed outputs (partial). structuredContent mirrors the text JSON, and coverage is deliberately partial: 187 tools declare an outputSchema and 187 tools carry annotations. Tools outside the schema set return text JSON without a declared output schema — see docs/TOOLS.md per tool.
  • Toolset profiles. REA_TOOLSETS filters registration to a profile slice (comma-separated union; unknown names fail startup instead of silently falling back to all). Resources and prompts are not filtered. New tools land in all only (fail-closed).
  • Roots (legacy + modern). With REA_ROOTS=1 on the legacy stdio path, client roots can only narrow REA_WORKSPACE_ROOT; they can never widen it. Modern-protocol Roots uses the SDK multi-round-trip flow (inputRequired + inputResponses); notifications/roots/list_changed only exists pre-2026, so refresh happens on the next MRTR round.
  • Progress (generalized). Stage helpers (createStageProgress/onAbort) pace notifications (~20/s) and clean up on cancel; rea_process_run pilot unchanged, rea_scan_repo + rea_jadx_full staged. Other synchronous handlers remain out of scope.
  • Async jobs (opt-in). With REA_ASYNC_JOBS=1, five job tools (rea_job_start/status/result/cancel/list) run whitelisted tools (rea_process_run, rea_scan_repo, rea_behavior_run) through a bounded in-memory queue (2 concurrent). Default surface stays 191 tools; opt-in surface is 196.

🔧 Configuration

All configuration is environment variables — no config files to edit in the server itself.

VariablePurpose
DBG_BRIDGE_TOKENBearer token for the HTTP transport (unset on HTTP = auth off + startup warning + only 44 read-only allowlist tools registered, intersected with REA_TOOLSETS; stdio is unaffected)
DBG_BRIDGE_FRIDA_TIMEOUT_MSFrida agent RPC timeout (default 30000)
REA_GHIDRA_DIRGhidra installation directory for provider-backed analysis
REA_UPX_BIN · REA_WABT_BIN · REA_AAPT2_BINExplicit tool paths when not on PATH
REA_JEB_MCP_URL · REA_JEB_ALLOW_REMOTEJEB endpoint; remote (non-loopback) requires REA_JEB_ALLOW_REMOTE=1
REA_CDP_URLAttach browser tools to an existing Chrome DevTools endpoint
REA_CORELIB_DLLPreferred .NET runtime DLL for CIL inspection
REA_WORKSPACE_ROOTWorkspace root(s), path-delimiter separated. When set, rea_* path arguments, the conduit open_target/debug_open paths, and user-visible derived writes (.unpacked, .extracted, HAR output) must resolve inside a root; unset = no restriction. Operator temp/cache surfaces stay outside this boundary by design (browser artifacts dir, Ghidra tmp project/input dirs, the hopper tmp request file, the apktool framework cache)
REA_ROOTSSet to exactly 1 to enable the legacy-stdio Roots pilot. Client file:// roots intersect with and can only narrow REA_WORKSPACE_ROOT; modern-protocol Roots is not enabled by this flag
REA_TOOLSETSComma-separated tool profiles to register: all (default, 191), minimal (8), static (98), android (27), dotnet (20), web (26), debug (50). Combined profiles union; an unknown or empty name fails startup. Resources/prompts are unaffected
REA_ASYNC_JOBSSet to exactly 1 to register the 5 async job tools (192 tools total). Jobs are in-memory only, at most 2 concurrent, and the whitelist is rea_process_run + rea_scan_repo + rea_behavior_run
REA_AUDIT_LOGPath of a JSONL audit log (both transports). Each line carries only ts, transport, tool, durationMs, isError — never arguments, tokens, paths, or target content. A write error warns once and disables auditing instead of crashing the server
REA_HTTP_RATE_LIMIT_PER_MINHTTP requests per client IP per minute (default 120); excess gets 429. A non-positive-integer value fails startup
REA_HTTP_MAX_CONCURRENTMaximum simultaneous in-flight HTTP requests (default 16); excess gets 429. A non-positive-integer value fails startup

External tools are discovered from these variables and PATH only — no machine-specific paths are baked in.

🔒 Security model

rea-plus is a debugger: by design it can launch, attach to, and instrument local processes. Treat access to it like shell access.

  • stdio first. The default transport never opens a port.
  • HTTP is locked down. Bearer token (constant-time compare), localhost Host/Origin validation against DNS-rebinding/CSRF, per-IP rate and concurrency limits (REA_HTTP_RATE_LIMIT_PER_MIN, REA_HTTP_MAX_CONCURRENT), and — when started without a token — a loud warning plus a reduced surface of 44 read-only, path-free allowlist tools (intersected with REA_TOOLSETS) instead of all 187.
  • Workspace boundary (opt-in). With REA_WORKSPACE_ROOT set, rea_* path arguments, the conduit open_target/debug_open paths, and user-visible derived writes must stay inside the root (realpath-checked, so junction/symlink escapes fail). Operator temp/cache surfaces (browser artifacts, Ghidra tmp dirs, the hopper tmp request file, the apktool framework cache) are a documented exception and are not forced inside the root.
  • Audit without content. REA_AUDIT_LOG records one JSONL line per tool call with only time, transport, tool name, duration, and isError — never arguments, tokens, paths, or target content.
  • Inputs are validated. Addresses that reach backend command languages are restricted to hex/decimal/symbol form — no ;/! command injection into r2/rizin.
  • SSRF gate. Outbound helper calls (e.g. the JEB bridge) are loopback-only unless the operator opts in; link-local/metadata hosts are always blocked.
  • No fake results. Missing capability ⇒ capability_unsupported with a reason; handler errors ⇒ MCP isError with the message only (no stack traces).
  • No target execution in static paths. Inspection tools read bytes; they never run the sample. Run unknown binaries in a VM — that is what the live lane is for.

🧪 Tests

97 test files. The default lane (npm test) runs 91 files and excludes the live-injection/debugger, packet-capture, browser, e2e, and local-Ghidra suites — those touch real processes or machine-specific installs and belong to a VM or a dedicated CI job (npm run test:live). Every file is capped at 90s with process-tree kill, so a hung backend can never hang the lane. The released line's CI runs the default lane on Ubuntu (Node 20 + 22).

npm test                        # default lane: 91 files (live suites excluded)
npm run test:live               # everything, incl. frida/sniff/browser/e2e/ghidra (VM/CI only)
npm run test:e2e                # spawn -> /health -> tools/list
node --test tests/evm.test.mjs # single-domain runs work too

❓ FAQ

Do I need Ghidra, IDA, Hopper, or JEB? No. Static JS/.NET/WASM/EVM and offline inspection work without them; provider-backed depth uses your own installations when present. Commercial tools are never bundled or licensed by rea-plus.

Why does a tool return capability_unsupported? Its backend is not installed on this machine. The response names the missing capability and where to get it (the same catalog doctor reads). Install it and the tool lights up — no code changes.

Why do live operations need confirm:true? They mutate a running target (breakpoints, stepping, memory writes). The gate keeps agents from changing program state by accident.

Does it clash with conduit? No. Conduit defaults to port 3847; rea-plus serves 3848, and the 30 conduit tool names are frozen.

npm says the package is not found? Update your cache — rea-plus@0.8.2 is on the npm registry and published on the MCP Registry. Use npx -y rea-plus everywhere above or the GHCR image.
